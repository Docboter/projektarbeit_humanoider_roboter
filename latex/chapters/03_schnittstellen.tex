\section{Policy-Server}
\label{sec:if-server}
\label{sec:simulation}

Der Policy-Server verbindet Modell und Simulation. Er lädt einen Checkpoint, nimmt
Beobachtungen entgegen und antwortet mit den nächsten Gelenkzielen. Die Simulation selbst
enthält kein Modell, sie fragt den Server in festem Takt. Ein Roboter könnte später auf
dieselbe Weise angebunden werden (\cref{sec:if-roboter}).

\subsection{Ablauf im Regelkreis}
\label{sec:if-server-ablauf}

Ein Durchlauf des Regelkreises besteht aus vier Schritten:

\begin{enumerate}
  \item Die Simulation schickt die vier Kamerabilder, die 28 Gelenkwinkel und den
    Aufgabentext an den Server.
  \item Der Server berechnet daraus einen Block von 16 aufeinanderfolgenden Gelenkzielen für
    alle 28 Gelenke. Die Arm-Bewegungen sagt das Modell relativ zum aktuellen Zustand voraus;
    der Server rechnet sie mit dem mitgeschickten Zustand in absolute Ziele um. Jede Anfrage
    muss deshalb den aktuellen Zustand enthalten.
  \item Die Simulation führt die ersten 8 der 16 Ziele mit 30~Hz aus
    (\texttt{EXECUTION\_HORIZON}), das dauert 267~ms.
  \item Danach fragt sie neu an. Die nächste Antwort muss also innerhalb von 267~ms vorliegen.
\end{enumerate}

\subsection{Nachrichtenformat}
\label{sec:if-server-format}

Server und Client kommunizieren über \ac{zmq} im Muster Anfrage/Antwort (REQ/REP) auf Port
5555. Jede Nachricht ist mit msgpack kodiert und hat die Form
\doc{{"endpoint": <name>, "data": {...}}}. Der Endpunkt für den Regelkreis ist
\texttt{get\_action}; daneben gibt es \texttt{ping}, \texttt{reset},
\texttt{get\_modality\_config} und \texttt{kill}. Numpy-Arrays werden als
\doc{{"__ndarray_class__": true, "as_npy": <Bytes>}} übertragen, Fehler kommen als
\doc{{"error": <text>}} zurück. \Cref{tab:if-server} zeigt den Inhalt einer Anfrage und der
Antwort; einen lauffähigen Beispiel-Client enthält \doc{docs/schnittstellen.md}, Abschnitt~3.

\subsection{Start, Latenz und Zeitlimits}
\label{sec:if-server-betrieb}

Im Sim-Container startet der Server automatisch. Von Hand wird er im Quellbaum der passenden
Generation (\texttt{app/Groot-1.6} bzw.\ \texttt{app/Groot-1.7}) gestartet:

\begin{minted}{bash}
python gr00t/eval/run_gr00t_server.py --model-path <checkpoint> \
    --embodiment-tag NEW_EMBODIMENT --use-sim-policy-wrapper --port 5555
\end{minted}

Erst die Option \texttt{--use-sim-policy-wrapper} liefert das flache Format aus
\cref{tab:if-server}. Mit N1.6 auf einer RTX PRO 6000 und vier Denoising-Schritten dauert eine
Antwort im Mittel 74~ms, gemessen über \ac{zmq} aus der Simulation rund 88~ms. Das lässt gut
dreifache Reserve gegenüber den 267~ms. Teilt sich der Server die \acs{gpu} mit einem zweiten
Server, steigt die Latenz auf bis zu 188~ms
(\doc{docs/simulation/inferenz-optimierung.md}). Der Sim-Client wartet höchstens 20~s auf eine
Antwort; nach einem Timeout baut er die Verbindung neu auf.

\section{Sim-Eval}
\label{sec:if-sim}
\label{sec:validierung}
\label{sec:eval-methodik}

Die Sim-Eval bewertet ein Modell im geschlossenen Regelkreis (Closed Loop): Die Policy steuert
den simulierten Roboter, und die Simulation prüft laufend, wie weit die Aufgabe gediehen ist.
Ergänzend prüft das visuelle Gate ohne Simulation vorab, wie gut ein Modell mit Bildern aus der
Simulation zurechtkommt.

\subsection{Eingaben}
\label{sec:if-sim-eingaben}

Eine Layout-Datei legt je Testepisode die drei Würfel fest
(\texttt{episodes.<nr>.cubes}: $x,y$ in m, rot/grün/gelb; \texttt{cubes\_yaw\_deg}; dazu
\texttt{n\_train}). Die Lagen werden aus dem ersten Bild der echten Episode bestimmt (Farbe,
Strahl auf die Tischebene; Fehler 0,3--0,4~cm gegen bekannte Lagen). Standard der Messungen ist
\texttt{layout\_heldout\_dy3.json}: Testlagen, Würfel je Seite 3~cm nach außen
(\cref{sec:erg-registrierung}). Die Szene aus Lauf~70 setzt zusätzlich Tischgröße und
Handgelenkkamera (\texttt{SIM\_TABLE\_SIZE}, \texttt{SIM\_WRIST\_*}).

\subsection{Ausgaben und Bewertungsstufen}
\label{sec:if-sim-ausgaben}

Jeder Lauf schreibt eine JSON-Datei \texttt{results\_<zeit>\_<checkpoint>.json}
mit einem Kopf (Checkpoint, Layout, Parameter, exakte 95-\%-Intervalle nach Clopper-Pearson)
und einem Eintrag je Episode. Abgebrochene Episoden zählen in keiner Rate. Bewertet wird in
sechs Stufen vom Erreichen des Würfels bis zum fertigen Turm (\cref{tab:if-stufen}); jede Stufe
wird für sich geprüft.

\begin{table}[htb]
  \centering
  \begin{tabularx}{\linewidth}{lX}
    \toprule
    Stufe & Bedingung \\
    \midrule

\subsection{Visuelles Gate}
\label{sec:if-sim-gate}

Das Gate läuft ohne Isaac~Sim und braucht nur wenige Minuten. Die Policy sagt für dieselben
Zustände einmal auf den Sim-Prüfbildern (\cref{tab:datensaetze}; 4 Episoden à 600 Schritte,
Würfel 5~cm und 4~cm) und einmal auf den echten Bildern derselben Episoden die nächsten
Aktionen vorher (teacher-forced, also ohne Rückkopplung). Kennzahl ist der Median der \ac{mse} über die
Hand-Dimensionen 14--27, gemittelt über die Seeds 0, 1 und 2 (Streuung etwa $\pm$5\,\%).
Bestanden ist das Gate, wenn die Kennzahl auf beiden Sim-Prüfsets unter 80\,\% des Werts der
Referenz derselben Generation ohne Co-Training liegt (N1.6 vision-v2 bzw.\ N1.7 vision-v1, je
@44000, Lauf~80) und auf Echtbildern nicht deutlich steigt. Ergebnis:
\texttt{visgate\_*.json}.

\section{Echter Roboter}
\label{sec:if-roboter}

Eine Anbindung an den G1 fehlt. Eine Roboter-Seite müsste die vier Kamerabilder und die 28
Gelenkwinkel lesen, sie nach \cref{tab:if-server} an den Server schicken und die
zurückkommenden Gelenkziele mit 30~Hz an Arme und Hände geben. Die gemessene Latenz lässt
rund dreifache Reserve, solange der Server die \acs{gpu} allein nutzt
(\cref{sec:if-server-betrieb}). Beine und Gleichgewicht regelt
die Policy nicht.
